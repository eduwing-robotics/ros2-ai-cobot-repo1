# 로봇 제어 피드백 로컬 전송 — 2026-09-13

## 문제와 관측 범위

실행 4eee67a8-f3f5-4e8a-9b4b-bc0cab36be08은 HBM-03 픽업 후 TrayHome 검사 중 새 피드백을 250ms 동안 받지 못했다. latest_age_ms=254.503, baseline_sequence=current_sequence=258555였다. GPU-01/HBM-01/HBM-02까지 배치 동작 완료였으며 HBM-03 보유 후보와 복구 필요 상태가 남았다.

기존 Fast DDS 비차단 송신 설정은 드라이버와 API 프로세스에 적용돼 있었다. 정지 상태 45초 네이티브 계측에서 드라이버 4,499회 발행, 최대 발행 간격 16.03ms/발행 소요 3.88ms였다. 실제 API rcl_take 최대 간격은 109.83ms였다. 독립 비교에서 MultiThreadedExecutor 수신 메시지 발행 후 나이가 최대 99.28ms였고, SingleThreadedExecutor는 5.20ms였다. 이 관측 동안 실제 실패의 250ms 공백 자체는 재현하지 못했다. 모든 과거 실패의 유일 원인을 확인했다고 주장하지 않는다.

## 변경

제어용 동일 호스트 피드백을 원격 DDS와 API ROS executor에서 분리했다.

- 드라이버는 SDK 상태를 읽어 만든 기존 RobotNonrtState 전체를 CDR로 직렬화해 Linux abstract Unix datagram으로 먼저 보낸다. 이후 기존 ROS 토픽을 그대로 발행한다.
- sendmsg는 MSG_DONTWAIT로 수행한다. 수신 프로세스가 없거나 큐가 가득 차도 로봇 상태 타이머를 전송 대기로 막지 않는다.
- API는 전용 수신 스레드를 사용한다. Unix 경로를 선택하면 ROS 피드백을 섞거나 자동 대체하지 않는다.
- 헤더에는 버전·드라이버 인스턴스·증가 순번·CLOCK_MONOTONIC 발행 시각·CDR 길이를 담는다. 250ms보다 오래되거나 미래인 데이터, 중복/역순, 다른 드라이버 인스턴스, 잘못된 길이, 드라이버 reconnect_flag를 거부한다.
- 상태 최신성에는 콜백 실행 시각이 아닌 드라이버 발행 시각을 사용한다. 기존 PortExecutor의 250ms 제한과 수신 간격 오류 표시는 유지한다. 운영체제·실제 장비 통신이 지연되면 계속 중단해야 한다.
- API 상태의 feedback_transport에 수신 개수, 거부 개수, 최대 발행/수신 간격, 최대 전달 나이, 최신 원본 나이, 수신 오류를 추가했다.

## 적용

이 PC의 config/ksmc.env에 `export KSMC_LOCAL_FEEDBACK_SOCKET=fr5_feedback_domain5`를 저장했다. 통합 런처와 드라이버/API 개별 런처 모두 이를 읽는다. 새 드라이버와 API가 같은 Linux 호스트에서 같은 이름을 사용해야 한다. 다른 셀에는 고유 이름을 사용한다. 미설정 시 기존 ROS 피드백 경로를 사용한다. 실행 중 새 드라이버 인스턴스로 바뀌면 API도 재시작해야 한다.

드라이버·API를 빌드·설치하고 로봇 정지·활성 worker 부재를 확인한 뒤 두 서비스 및 엔드포인트를 재시작했다. 비전 프로세스는 유지했다. 기존 실패 기록은 삭제하지 않았고 recovery_required=true를 보존했다. API 재시작 후 메모리의 held_candidate가 null이어도 HBM-03이 물리적으로 비어 있다는 증거가 아니다. 복구 전 현장 확인이 필요하다.

## 검증

- 전체 오프라인 회귀 980개 통과, Python 197개 파일·쉘 문법 검사 통과.
- 실제 Unix 소켓 독립 수신, 발행 시각 기반 신선도, 지연/재전송/드라이버 변경/잘못된 데이터 거부, 중복 수신기 방지 및 기존 sticky gap 검사를 포함했다.
- 원본 증거: runtime/feedback_latency_20260913/. 로봇 이동·그리퍼 동작·복구·새 조립 시작은 이 수정에서 수행하지 않았다.
- SDK GetRobotRealTimeState의 내부 수신 시각 자체는 이번 전송 헤더로 증명하지 않는다. 헤더 시각은 SDK 상태를 읽은 드라이버 발행 시각이다. 실제 네트워크 단절이나 운영체제 정지를 무시하지 않는다.

- 수정 적용 후 동시 180초 DDS 비교: 단일 실행기 최대 수신 공백 224.03ms, 다중 실행기 222.32ms. 다중 실행기의 발행 후 데이터 나이는 최대 90.81ms였다. 같은 기간 제어용 로컬 피드백은 최대 수신 공백 25.57ms였다. 이 비교에서도 DDS 250ms 초과는 0회이며, 과거 실패의 정확한 타이밍을 재현한 시험은 아니다.

- 최종 부하 검증: 300.01초, 상태 조회 1443회 모두 최신·정지·진행작업 없음, 조회 시간초과 0회. 로컬 누적 피드백 39,469개, 거부 0개, 최대 수신 간격 25.570ms, 최대 전달 나이 7.725ms. 누적 개수는 검증 전 API 기동 구간도 포함한다. 상태 서비스 응답은 최대 1.459초 걸렸으나 제어 피드백 수신은 분리돼 유지됐다. local_validation.json 및 local_validation_samples.json.
