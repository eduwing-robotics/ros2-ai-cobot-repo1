## 5. 공통 복구 명령 확장

- 초기 `assembly.recover`는 정상 준비된 하위 로봇 상태만 허용해 수동 중지 사건의 하위 복구 요구를 처리하지 못했다. 이를 공통 명령 내부에서 처리하도록 확장했다.
- 작업자의 최신 현장 정리 확인 → 현재 실행 worker 종료 및 잠금 확인 → 정상 정지 검증 → abnormal_stop만 남은 경우 오류 리셋 → 새 피드백으로 정상 정지 검증 → 같은 실행의 종료된 파지/복구 기록 정리 → 소유권 보존 이동 순서다.
- 비상정지·안전문·안전영역·다른 활성 오류, 실제 이동, 오래된 피드백, 살아 있는 worker, 다른 실행의 미해결 기록, 결과를 모르는 intent는 차단한다.
- 같은 ID 재실행이나 자동 재개를 하지 않는다. 정상 완료 결과는 유지하며, 실패한 실행은 `failed_recovered`로 정리한다. 정상 완료는 원래 새 ID Start를 차단하지 않는다.
- 초기 공통 복구 테스트 72개, 수동 중지 확장 후 83개 통과. 서버 반영·조회 확인 완료.

현장 정리 후 프로젝트 루트에서:

```bash
./recover_assembly.sh --confirm-scene-ready --operator-id juchan
```

- Unity: `/real/assembly/command`, `fr5.assembly_execution/v2`, `action=assembly.recover`. 같은 현재 execution_id와 120초 이내 scene_confirmation을 보낸다.
- `recovery_applied=true`를 확인한다. 보존된 이전 `EXECUTION_FAILED`만으로 복구 실패를 판단하지 않는다.
- 문서: [복구 명령·Unity 요청 형식](../docs/ASSEMBLY_RECOVER_KO_20260910.md).
- 증거: `runtime/assembly_recovery_20260910/`, `runtime/manual_stop_recovery_deploy_20260910/`. 이후 개별 복구 감사 기록: `runtime/manual_stop_recovery/`.

## 6. 생산 취소 및 일시정지·이어하기

### 실행 중 취소

- `assembly.cancel`을 추가했다. 실행 ID, 제어 UUID(control_id), 증가하는 control_sequence로 요청을 구분한다. 동일 요청 재전송은 물리 명령을 반복하지 않는다.
- 다음 명령 전송 차단 → StopMotion → launcher SIGINT → 실제 정지 검증을 수행한다.
- `CANCEL_STOP_CONFIRMED`는 로봇 정지 확인이다. worker 종료나 현장 복구 완료와 동일하지 않다. 종료 후 현장 정리·복구가 필요하며 같은 실행을 이어갈 수 없다.
- 서버 `cancel=true` 확인. 증거: `runtime/production_cancel_deploy_20260910/`.

### 실기 시험 및 최종 일시정지 모드

- 사용자가 빈 그리퍼·장애물 없는 현장을 확인하고 짧은 이동 시험을 승인했다.
- 기존 위치 부근에서 J1 최대 1.5도, 속도 1%, 3개 MoveJ의 기존 blend 50/50/0 패턴으로 시험했다. 그리퍼 동작·전체 조립은 실행하지 않았다.
- 직접 PauseMotion 시험은 수락 응답 0에도 정지 검증 또는 건강 상태 검사에 실패했다. 취소 정지로 안전 정지를 확인하고 서비스를 복원했다. 직접 retained 방식은 활성화하지 않았다.
- **이동 완료 지점 대기 모드**를 추가했다. 다음 명령 전송을 막되 이미 전송된 이동을 마치게 하고, 0.5초 이상 실제 정지 및 그리퍼 상태를 확인한 뒤 PAUSE_CONFIRMED를 반환한다.
- 이어하기는 동일 실행 프로세스, 레시피, 좌표, 그리퍼/파지 정체성, 해당 관측 유효성을 검사하고 전송 차단을 해제한다. PauseMotion/ResumeMotion을 호출하지 않는다.
- 실기 응답: PAUSE_CONFIRMED → RESUME_CONFIRMED → PAUSE_CONFIRMED → CANCEL_STOP_CONFIRMED. 각 동일 제어 요청 재전송 시 추가 하드웨어 명령이 없는 것을 확인했다.
- 취소 후 예상된 abnormal_stop 때문에 시험 코드의 건강한 관절 읽기가 실패했다. 이 실패를 숨기지 않고 원시 피드백으로 정지를 별도 확인했다: 마지막 약 0.5초 51개 샘플 모두 motion_done=1, XYZ 변화폭 약 0.0044/0.0070/0.0097 mm. 이후 오류 리셋과 정상 정지 확인 완료.
- 최종 모드 회귀 테스트 72개 통과. 이 숫자와 앞 단계의 테스트 수는 범위가 다른 실행 결과이며 누적 합산하지 않는다.
- `KSMC_WHOLE_CYCLE_BOUNDARY_PAUSE=true` 설정과 서버 재시작 후 생산 pause/resume/cancel 모두 true, pause_behavior=after_dispatched_motion 확인.
- 짧은 빈 그리퍼 시험을 실제 부품 파지 중 모든 상황이나 전체 25개 생산 사이클 검증으로 확대 해석하지 않는다.
- 문서: [생산 제어 API·최종 모드](../docs/ASSEMBLY_CONTROL_KO_20260910.md).
- 증거: `runtime/pause_commission_20260910/commissioning_result.json`, `boundary_verified_trial.json`, `boundary_verified_samples.json`, `runtime/boundary_pause_deploy_20260910/verification.json`.

## 다음 작업 시작점

1. Unity에서 생산 capability와 pause_behavior를 사용해 UI를 연결하고 control_id/sequence 및 pause_control_id로 응답을 대응한다. Unity UI 연결 완료 자체는 이번 로봇 서버 검증으로 보장하지 않는다.
2. 새 전체 시험 전 기판·트레이·그리퍼를 실제로 정리하고 새 ID/현장 확인으로 시작한다. 이전 9개 완료 기록을 물리적 현재 배치로 가정하지 않는다.
3. 단일 MoveL 변경 후 체감 끊김과 전체 사이클 중 일시정지·이어하기는 실제 생산 관측을 더 남긴다. PM-01 충돌 원인은 별도 확인한다.
4. 재부팅 후 API 시작: `bash run_fr5_assembly_stack.sh api-start`. 전체 장치 시작 절차는 [스택 명령](../docs/FR5_ASSEMBLY_STACK_COMMANDS.md)을 따른다. 프로세스가 재부팅 뒤 자동 유지된다고 가정하지 않는다.
