# 계층 간 통합 계약

이 문서는 변경 가능한 주소·메시지 형식보다 계층 사이에서 보존해야 할 의미를 정의합니다. 구체 식별자와 payload는 제공 컴포넌트의 API 문서와 소스가 기준입니다.

## 요청 등록 계약

- 호출자가 UUID `job_id`를 생성합니다.
- 요청은 제품, 목표 PASS 수량과 레시피 버전을 식별합니다.
- MainServer는 요청을 검증하고 `PENDING` Job을 등록합니다.
- 같은 `job_id`와 같은 내용의 재시도는 멱등하게 처리합니다.
- 같은 `job_id`에 다른 내용을 보내면 거절합니다.
- 등록 성공은 실행 수락이나 생산 완료를 뜻하지 않습니다.

## 실행 계약

- Sequencer만 Job과 Unit 실행 상태를 전이합니다.
- Sequencer는 레시피 snapshot을 검증한 뒤 실행을 시작합니다.
- 상위 흐름은 backend의 의미 단위 공개 동작만 호출합니다.
- backend는 입력 검증부터 실제 완료·실패·timeout 전달까지 완결합니다.
- 동작이 실제로 끝나기 전에 성공을 반환하지 않습니다.

## 진행과 결과 계약

모든 비동기 진행과 결과는 `job_id`로 현재 작업과 대조할 수 있어야 합니다. 진행 상태는 표현을 위한 정보이며 생산 상태의 별도 원본이 아닙니다.

최종 결과는 다음 의미를 구분합니다.

| 결과 | 의미 |
|---|---|
| 실행 성공 | 요청한 물리 동작과 검사가 실제로 끝남 |
| 검사 FAIL | 실행은 완료됐지만 품질 목표를 통과하지 못함 |
| 실행 실패 | 설비 동작을 완료하지 못함 |
| timeout | 제한 시간 안에 실제 완료를 확인하지 못함 |
| 안전정지 | 작업 상태를 유지한 채 신규 동작을 차단함 |

## 조회 계약

조회는 저장된 생산 사실과 현재 실행 snapshot을 반환할 수 있지만 상태를 전이하지 않습니다. 조회 실패가 실행 중인 설비의 상태를 바꾸거나 생산 기록을 추정하게 해서는 안 됩니다.

## 수동 제어 계약

수동·저수준 제어와 자동 조립은 별도 계약입니다. 자동 Scenario는 수동 제어 API를 조합해 공정 순서를 만들지 않습니다. 수동 제어는 활성 모드, 안전 조건, 목표값과 실제 완료를 확인할 수 있어야 합니다.

## 데이터 기록 계약

- MainServer는 Job 등록과 조회를 담당합니다.
- Sequencer는 Unit, 검사, 재고와 Job 실행 결과를 기록합니다.
- backend callback은 DB 작업 때문에 안전정지나 설비 정리를 지연시키지 않습니다.
- 레시피 본문, 좌표, 단계 checkpoint와 실시간 스트림은 생산 DB에 저장하지 않습니다.

## 변경 가능한 구현 세부사항

HTTP 경로, ROS 인터페이스 이름, 메시지 schema, 프로세스 수와 배포 위치는 구현 세부사항입니다. 이를 변경할 때도 위의 멱등성, 단일 실행, 실제 완료, 실패 전달과 데이터 소유 경계는 유지해야 합니다.

상세 계약은 [MainServer API](../MAIN_SERVER/Main_serverAPI.md)와 [Assembly Sequencer API](../ASSEMBLY_SEQUENCER/API.md)를 따릅니다.
