# 프로젝트 설계 개요

이 시스템의 목표는 작업자의 생산 요청을 안전한 설비 동작으로 연결하고, 실제 조립·검사 결과를 추적 가능한 생산 사실로 남기는 것입니다. Mock과 Real은 구현 방식이 달라도 같은 업무 의미와 완료 기준을 제공합니다.

## 세 계층

| 계층 | 책임 | 포함되는 영역 |
|---|---|---|
| 요청·표현 | 사용자 의도 수집, 입력 검증, 상태와 결과 표시 | UnityDT, MainServer |
| 업무·조정 | 생산 요청 선택, Job·Unit 상태 전이, 레시피 순서 조정 | Assembly Sequencer |
| 실행·설비 | 의미 단위 동작, 좌표 변환, 통신 재시도, timeout과 안전정지 | 로봇·비전·컨베이어 backend |

전송 브리지와 데이터베이스는 계층을 대체하지 않는 기반 계약입니다. 통신 방식이나 프로세스 배치가 바뀌어도 위 책임은 유지되어야 합니다.

## 생산 실행 불변 조건

- `production.jobs`가 영속 생산 요청의 유일한 진입점입니다.
- MainServer는 클라이언트가 만든 UUID `job_id`로 `PENDING` Job을 등록합니다.
- 같은 `job_id` 재요청은 동일 요청이면 기존 Job을 반환하고, 내용이 다르면 거절합니다.
- Sequencer만 Job과 Unit의 실행 상태를 전이합니다.
- 동시에 실행 중인 Job은 하나이며, 한 Job에서 실행 중인 Unit도 하나입니다.
- `requested_quantity`는 생산 시도 수가 아니라 검사 PASS 목표 수량입니다.
- 검사 FAIL Unit은 완료된 시도로 보존하고 같은 Job에서 다음 Unit을 시작합니다.
- 실행 자체가 실패한 Unit은 `FAILED`로 기록합니다.

## 레시피와 실행

레시피는 조립 순서와 부품·슬롯의 의미를 정의합니다. Sequencer는 Job을 시작할 때 고정된 레시피를 검증하고 처음부터 순서대로 실행합니다.

생산 DB는 레시피 본문, 설비 좌표와 단계 checkpoint를 복제하지 않습니다. 실행 계층은 좌표 변환, 설비 통신, 재시도, timeout, 실제 완료 감지와 안전정지를 완결합니다.

## 완료와 실패

요청 수락은 실행 완료가 아닙니다. 상위 계층에 성공을 반환하려면 backend가 의미 단위 동작의 실제 완료를 확인해야 합니다. 실패와 timeout은 원인을 잃지 않고 상위 계층까지 전달합니다.

Sequencer가 재시작되면 실행 중이던 Unit은 실패로 마감하되 Job은 유지합니다. 설비 준비와 reset을 확인한 뒤 새 Unit으로 레시피 첫 단계부터 실행하며 불명확한 중간 상태를 자동 재개하지 않습니다.

안전정지 중에는 Job과 Unit을 `RUNNING`으로 유지합니다. 안전 상태 해제만으로 자동 재개하지 않으며, 설비 상태를 확인한 공개 경계를 통해 재개합니다.

## 데이터 경계

| 데이터 | 소유자 |
|---|---|
| 제품·부품·슬롯·Job·Unit·검사·재고 사실 | production 데이터 계약 |
| 레시피와 조립 순서 | Assembly Sequencer와 Git |
| 설비 좌표·보정 | 실행 backend와 설비 설정 |
| 실시간 관절·TCP·진행 스트림 | 런타임 상태 |
| 작업자 화면 상태 | UnityDT |
| 부품 데이터시트와 불량대책서 | MainServer가 관리하는 파일 계약 |

## 문서 소유 원칙

- 전체 시스템 설계와 계층 간 계약은 `docs/`가 소유합니다.
- 한 컴포넌트의 공개 계약과 운영 방법은 해당 컴포넌트가 소유합니다.
- 과거 설계는 `archive/`, 조사 결과는 `reports/`에 둡니다.
- 실행 코드와 충돌하는 문서는 기준 문서가 될 수 없습니다.
