# 불량대책서 표준양식 — 필드 매핑

`불량대책서_표준양식.xlsx`의 `{{token}}`을 `scan_quality.py`가 치환한다.
샘플: `불량대책서_표준양식_샘플.xlsx`

**두 파일은 손으로 고치지 않는다.** 둘 다 `build_report_template.py` 한 정의에서 나온다.

```bash
uv run MAIN_SERVER/templates/build_report_template.py
```

의존성(`openpyxl` · `pillow`)은 스크립트 상단 PEP 723 블록에 있어 `uv` 가 알아서 받는다.
저장소 `.venv` 에는 없다 — 문서 양식을 뽑자고 서버 환경에 넣을 이유가 없다.

따로 편집하다가 셀 좌표가 어긋난 적이 있다. 양식을 바꿀 일이 생기면 빌더를 고치고 다시 돌린다.

시트는 5장이고 **결재 대상은 「대책서」 1장**이다. 별지 3장은 담당자가 원인을 좁히는 데 쓰는
별지이며, 자동 조회 결과라 사람이 손대지 않는다.

**별지 3장은 불량 유형과 무관하게 항상 첨부한다.** 어느 자료가 이번 건에 쓸모 있는지는
담당자가 판단한다. 시스템이 미리 골라 주면, 고르는 규칙이 틀렸을 때 담당자는 그런 자료가
있었다는 사실조차 모른다.

| 시트 | 용도 | 자료 성격 | 원본 |
|---|---|---|---|
| 대책서 | 보고·결재 (A4 1장) · ①~④ | 발행 시점 고정 | `defect_report.alerts` + 담당자 회신 |
| 검증 | ⑤ 효과 검증 · ⑥ 종결 | 적용 후 2~4주에 채움 | `alert_countermeasures` 검증·종결 컬럼 |
| 근거 | 어느 유닛·슬롯에서 났는지 | 발행 시점 고정 | `defect_report.alert_evidence` |
| 판단자료 | 언제부터·무엇이 바뀌어서 났는지 (A~C) / 무엇을 확인해야 하는지 (D) | A~C 고정 · D 참조 | `production` 집계 + 과거 `alerts` + `part_catalog.quality_checklists` |
| 대체품 | 부품을 바꿔야 할 때의 선택지 | 조회 시점 참조 | `part_catalog.part_candidates` + `sources` |

**고정과 참조를 섞지 않는다.** 고정 자료는 발행 시점 스냅샷이라 나중에 집계가 바뀌어도
덮어쓰지 않는다([3개 스키마 설계](../../UnityDT/Docs/DB3.md#스냅샷을-저장한다)). 참조 자료는 데이터시트를 다시
적재하면 값이 바뀌므로, 시트 상단에 조회 시각과 데이터시트 기준일을 반드시 함께 싣는다.

## 좌표로 읽지 않는다 — 담당자 회신 칸

담당자가 행을 하나만 삽입해도 좌표는 밀린다. 회신 칸은 **정의된 이름**으로 읽고 쓴다.
Excel이 이름을 따라 움직이므로 삽입·삭제에 깨지지 않는다.

| 정의된 이름 | 시트 · 셀 | 항목 | 회신 후 반영할 컬럼 |
|---|---|---|---|
| `reply_containment_scope` | 대책서 B21 | ① 협조 필요 체크 라인 | `containment_summary` 첫 줄 |
| `reply_containment` | 대책서 B22 | ① 초동 조치 | `alert_countermeasures.containment_summary` |
| `reply_root_cause_label` | 대책서 B25 | ② 발생 원인 — 한 줄 요약 (40자) | `alert_countermeasures.root_cause_label` |
| `reply_root_cause` | 대책서 B26 | ② 발생 원인 | `alert_countermeasures.root_cause_summary` |
| `reply_escape_cause` | 대책서 B28 | ③ 유출 원인 | `alert_countermeasures.escape_cause_summary` |
| `reply_prevention` | 대책서 B31 | ④ 재발방지 대책 | `applied_recipe_version` + `applied_at` |
| `reply_verify_period` | **검증** B5 | ⑤ 검증 기간 | (검증 집계 구간) |
| `reply_verify_recipe` | **검증** D5 | ⑤ 적용 레시피 | `applied_recipe_version` |
| `reply_verify_inspected` | **검증** E5 | ⑤ 검증 수량 | `verified_inspected_quantity` |
| `reply_verify_defective` | **검증** F5 | ⑤ 불량 수량 | `verified_defective_quantity` |
| `reply_verify_status` | **검증** H5 | ⑤ 판정 | `verification_status` |
| `reply_verify_note` | **검증** B6 | ⑤ 판정 근거 | (본문 보관 안 함) |
| `reply_closed_at` | **검증** F8 | ⑥ 종결일 | `alerts.closed_at` + `alert_status='CLOSED'` |
| `reply_closure_note` | **검증** B9 | ⑥ 종결 의견 | `alert_countermeasures.closure_note` |

**B25 협조 체크 라인**은 담당자가 혼자 결정할 수 없는 조치다. 생산 중단 · 출하 보류 ·
재고 선별 · 고객 통보 · 설비 정지. `☐` 를 `☑` 로 바꾼 항목만 골라
`containment_summary` 첫 줄에 `[협조 요청] 생산 중단 · 출하 보류` 형태로 붙인다.
초동조치는 품질 담당자 혼자 실행하는 일이 아니라 주관하는 일이라, 그 사실이 문서에
남아야 한다.

`verified_defect_rate`는 「검증」 G5 수식(`=F5/E5`)이 아니라 **파서가 다시 계산해서** 넣는다.
회신본을 수식 평가 없이 읽으면 G5는 빈 값이거나 캐시값이다.

`closed_by`는 시트에 칸이 없다. 결재란(F1:H3) 서명이 종이 절차라 회신본에서 읽을 수 없다.
회신 처리하는 사람이 API 호출자로 채운다.

### 폼이 자기 자신을 설명하지 않는다

한때 밴드마다 부제가 붙어 있었다 — `시스템 자동 집계 · 수정 금지`, `아래 크림색 칸만
채우시면 됩니다`, `잔여 위험을 확인하고 닫습니다`. 전부 뺐다.

**시트 보호가 걸려 있어 자동 집계 칸은 물리적으로 입력이 안 되고**, 회신 칸만 크림색이라
색이 이미 그 말을 하고 있다. 폼이 자기 UI를 글자로 다시 설명하면 줄만 늘고 읽는 사람은
정작 데이터를 늦게 만난다. 인쇄되는 것은 자료여야지 사용 설명이 아니다.

푸터의 `MAIN_SERVER/scan_quality.py` 도 뺐다. 결재 문서에 내부 소스 경로가 인쇄될 이유가 없다.

### 안내문은 셀에 적지 않는다

작성 요령은 셀 값이 아니라 **입력 메시지**(데이터 유효성 → 설명 메시지)로 붙어 있다.
칸을 클릭하면 뜨고, 인쇄되지 않고, 지울 것이 없다.

셀에 회색 안내문을 적어 두던 방식은 두 가지로 샜다. 담당자가 지우지 않으면 그대로 결재에
올라갔고, 파서가 그 안내문을 '발생 원인'으로 저장했다.

파서는 회신 칸이 비어 있으면 **비어 있는 것으로 처리한다.** 기본값을 넣지 않는다.

### 시트 보호

네 시트 모두 보호가 걸려 있다(암호 없음). 회신 칸만 잠금이 풀려 있다.
자동 집계 칸과 「검증」 G5 수식은 잠겨 있다.
별지 3장은 정렬·필터만 허용한다.

## 선행 조건 — `part_id` ↔ `group_id` 연결

「대체품」·「판단자료 D」는 `alerts.part_id`에서 `part_catalog`로 넘어갈 수 있어야 성립한다.

- `production.parts.part_id` = `HBM` `PM` `GPU` `CAP` `IND` `VRM` (004_mock_seed.sql)
- `part_catalog.part_groups.group_id` = `C-001` 형태

데이터시트는 `semiconductor_assembly_quality_datasheet_*.xlsx` **한 파일**이다.
한때 `hbm_accelerator_package_board_datasheet.xlsx` 에 같은 내용이 복사돼 있었는데,
로더가 무엇을 정본으로 볼지 정할 수 없어 지웠다.

연결은 그 파일의 **「HBM Package Board BOM」 시트 `Group ID` 열**에서 온다.
그 시트는 이미 `part_id` 한 행 단위라 `part_group_links`와 grain이 같다.
Components 시트는 후보 한 행 단위(12행)라 여기에 `part_id`를 넣으면 값이 중복 반복된다.

```sql
CREATE TABLE IF NOT EXISTS part_catalog.part_group_links (
    part_id  text PRIMARY KEY,
    group_id text NOT NULL REFERENCES part_catalog.part_groups(group_id),
    load_id  bigint NOT NULL REFERENCES part_catalog.datasheet_loads(load_id)
);
```

**여섯 부품이 모두 연결된다.**

| part_id | group_id | 범주 | 대체 후보 | 이미지 |
|---|---|---|---|---|
| `CAP` | `C-001` | MLCC | 2종 | `UI/Icons/item-cap.png` |
| `HBM` | `M-001` | HBM | 2종 | `UI/Icons/item-hbm.png` |
| `PM` | `PM-001` | Power Module | 1종 | `UI/Icons/item-pm.png` |
| `GPU` | `G-001` | GPU Module | **단일 소스 · 대체 불가** | `UI/Icons/item-gpu.png` |
| `IND` | `L-001` | Power Inductor | 1종 (정격 상이) | `UI/Icons/item-ind.png` |
| `VRM` | `V-001` | Voltage Regulator | **조사 필요** | `UI/Icons/item-vrm.png` |

데이터시트가 이 보드의 BOM 6종만 싣도록 다시 짜였다. 이전에는 다른 보드를 보고 만들어져
있어서 `Boost IC` `AI 모듈` `전해 콘덴서` `ECC UDIMM` 처럼 이 보드에 없는 범주가 실려 있었고,
정작 `Power Module` `GPU Module` `Power Inductor` `Voltage Regulator` 는 없었다.

**대체 후보가 없는 것과 조사를 안 한 것은 구분해서 싣는다.** GPU 모듈은 OEM 계약 품목이라
대체 경로 자체가 없고(`단일 소스 · 대체 불가`), VRM 은 아직 안 찾아본 것(`조사 필요`)이다.
「대체품」 시트가 이 둘을 다르게 인쇄해야 한다 — 전자는 재고·리드타임 관리가 유일한 대책이고,
후자는 담당자가 할 일이 남아 있다는 뜻이다.

연결이 없는 부품이 생기면 「대체품」 시트를 `해당 데이터시트 없음`으로 비우고 발행한다.
**문서 발행이 이 연결에 막혀서는 안 된다.**

### 부품 이미지

`part_group_links.image_path` 는 데이터시트 BOM 시트의 `Image` 열에서 온다. 경로는 Unity
프로젝트의 `Assets/` 기준이고, 파일명이 `item-{part_id}.png` 로 `part_id` 와 1:1 이다.

대책서 표지의 **A1:A3 전용 칸**에 46×46px 로 가운데 얹고, 제목은 B1:D3 으로 옮겼다.
**담당자가 글자를 읽기 전에 어떤 부품인지 알아보게 하려는 것이다.**

한때 제목 블록(A1:D3) 왼쪽 여백에 겹쳐 뒀는데, 그러면 로고처럼 보이고 무엇을 가리키는지
애매하다. 칸을 나눠 두면 "이 문서가 다루는 부품"이라는 자리값이 생긴다.

파일이 없거나 Pillow 가 없으면 그림 없이 발행한다. 그림 때문에 문서가 막히면 안 된다.

## 시트 `대책서`

### 자동 집계 — 상단

읽는 순서를 바꿨다. 수치를 세로로 쌓아 두면 담당자가 자기 할 일을 찾으려고 스무 줄을
훑어야 한다. 지금은 **머리(누가·무엇) → 회신 기한 띠 → 현황(가로 한 줄) → 시스템 분석 →
담당자 작성 ①~④** 순이다. ⑤⑥ 은 「검증」 시트로 뺐다.

| 셀 | 토큰 | 원본 | 비고 |
|---|---|---|---|
| B5 | `{{alert_code}}` | `alerts.alert_code` | `QA-{part_id}-{defect_type}-{YYYYMMDD}-{NNN}` |
| F5 | `{{issued_at}}` | `alerts.issued_at` | |
| A1 | `{{part_image}}` | `part_group_links.image_path` | 46×46px. A1:A3 전용 칸 (제목은 B1:D3) |
| B6 | `{{part_id}}` `{{part_name}}` `{{group_id}}` `{{category_label}}` | `alerts.part_id` → `production.parts` → `part_group_links` | 두 줄로 감긴다 |
| F6 | `{{defect_type}}` | `alerts.defect_type` | 4종 목록 검증 |
| B7 | `{{assignee}}` | `alerts.assignee` | NULL이면 `배정 대기` |
| F7 | `{{support_teams}}` | `alerts.support_teams` | 협조 부서. `·` 로 구분한 한 줄 |
| **A9** | `{{alert_status}}` `{{due_initial}}` `{{due_cause}}` `{{due_action}}` | `alerts.alert_status` + 기한 4종 | **회신 기한 띠.** 기한을 여기 한 줄로 모은다 |
| B11 | `{{period_start}}` `{{period_end}}` `{{window_days}}` `{{evaluation_mode}}` | `alerts.period_*` + `thresholds` | `[start, end)` |
| F11 | `{{source_recipe_version}}` | `alerts.source_recipe_version` | ⑤ 효과검증 비교 기준 |
| A13 | `{{inspected_quantity}}` | `alerts.inspected_quantity` | 유닛 수 × 해당 부품 슬롯 수 |
| B13 | `{{defective_quantity}}` | `alerts.defective_quantity` | |
| C13 | `{{defect_ppm}}` | `defect_rate * 1e6` | 머리글에 기준 PPM 병기. 붉은 배경 |
| E13 | `{{vs_threshold_ratio}}` | `defect_rate / threshold_rate` | **기준 대비 배수** |
| F13 | `{{unit_impact}}` | 아래 참고 | **완제품 영향** |
| B14 | `{{hotspot}}` | 「근거」 슬롯 분포 상위 2~3개 | 예: `CAP-02 8건 · CAP-04 5건` |
| F14 | `{{trend_vs_prev}}` | 직전 동일 길이 구간 대비 + `first_exceeded_at` | 예: `200 → 1,280 PPM (6.4배 · 08-18 초과)` |
| B16 | `{{auto_analysis}}` | 스캐너 생성 4줄 | 아래 규칙 |

### 왜 %가 아니라 PPM · 배수 · 완제품 영향인가

배치 불량은 % 하나로 읽히지 않는다. 세 가지를 함께 실어야 한다.

- **PPM** — 업계가 쓰는 단위다. `0.128%` 보다 `1,280 PPM` 이 바로 읽힌다.
- **기준 대비 배수** — 기준이 수백 PPM 대로 내려가면 `%p` 차이는 `+0.09%p` 처럼 무의미해
  보인다. `3.2배` 는 자릿수와 무관하게 심각도를 전한다.
- **완제품 영향** (`{{unit_impact}}`) — 이 보드는 슬롯이 25개라 부품 하나의 불량률이
  완제품에서 증폭된다. 부품 400 PPM 이면 완제품 수율은 `(1-0.0004)^25 = 99.0%` 다.
  형식: `{inspected_unit_quantity}대 중 {affected_units}대 ({비율})`.

`{{affected_units}}` 는 `alert_evidence` 의 `unit_id` distinct 수다. 불량 건수와 다르다 —
한 유닛에 두 슬롯이 깨질 수 있다.

### 기한은 네 단계다

`initial_action_due_at` / `final_action_due_at` 두 컬럼으로는 ①~⑤ 의 속도 차이를 담을 수
없다. ⑤ 효과검증은 대책을 적용하고 **다시 생산이 돌아야** 채울 수 있어서, 3일 마감 안에
넣는 것은 물리적으로 불가능하다.

| 토큰 | 통상 기한 | 원본 | 어디에 |
|---|---|---|---|
| `{{due_initial}}` ① | 24시간. **붉은색** | `alerts.initial_action_due_at` | 9행 띠 |
| `{{due_cause}}` ②③ | 3~5일 | `alerts.cause_due_at` | 9행 띠 |
| `{{due_action}}` ④ | 1~2주 | `alerts.final_action_due_at` | 9행 띠 |
| `{{due_verify}}` ⑤ | 적용 후 2~4주 | **컬럼 없음 — 상수 문구** | 「검증」 A4 |

**기한은 9행 한 줄에 모은다.** 블록마다 흩어 두면 A열 라벨이 세 줄이 되고, 담당자는
일정을 여섯 군데서 주워 읽어야 한다. 붉은 마감은 ① 하나뿐이고 나머지는 회색이다.

`⑤` 만 컬럼이 없다. **`적용 후 2~4주` 는 `applied_at` 기준의 상대 표기인데, 그 값은 발행
시점에 존재하지 않는다.** 없는 것을 컬럼으로 만들지 않고 상수 문구로 둔다.

`alerts.document_path`에 생성 파일 경로를 기록한다.

### 1·2번 블록은 LLM 없이 생성한다

「1. 불량 현황」과 「2. 시스템이 먼저 본 것」은 시스템 자동 기입란이다. **모든 값이 조회 ·
집계 · 산술로 나와야 한다.** 문장 생성 모델을 붙이지 않는다.

그래서 규칙에 두 가지를 넣지 않는다.

- **요약** — 긴 원문을 짧게 줄이는 일. 계산이 아니라 판단이다.
- **DB에 없는 사실** — 모델을 붙여도 못 만든다. 없는 것을 지어내는 것이라 환각이다.

이 기준으로 훑었더니 두 값이 걸렸다. 둘 다 사람이 적는 칸으로 만들었다
(`008_recipe_versions_and_cause_label.sql`).

| 값 | 쓰이는 곳 | 걸린 이유 | 새 소스 |
|---|---|---|---|
| `{change}` | ② 줄 · 「판단자료」B `change_note` | `production.jobs` 에 `recipe_version` 텍스트뿐이었다. 변경 내역도 적용 시각도 없어서 **문장이 DB에 없는 사실을 말하고 있었다** | `production.recipe_versions.change_note` · `applied_at` |
| `{cause}` | ③ 줄 | 과거 문서의 `root_cause_summary` 를 한 줄로 줄인 값. 원문은 여러 문장이라 **요약이 필요했다** | `alert_countermeasures.root_cause_label` (40자) |

**값이 없으면 그 절만 빼고 낸다. 채우지 않는다.** `recipe_versions` 에 행이 없으면
`변경 내용 '…'` 을 빼고, `root_cause_label` 이 비어 있으면 `· {cause}` 를 뺀다.
줄 자체는 그대로 낸다 — [줄을 빼지 않는다](#auto_analysis-생성-규칙)는 원칙은 유지된다.

`recipe_versions` 는 `production.jobs` 가 참조하지 않는다(FK 없음). 등록되지 않은 버전으로
작업이 돌 수 있고, **문서 발행이 이 연결에 막혀서는 안 된다.**

③ 줄은 이 문서가 **과거 문서의 3번 칸을 읽는** 유일한 자리다. 시스템 자동 생성이 사람 입력에
의존하므로, 그 입력을 40자로 짧게 받는다. 담당자가 ② 를 쓸 때 한 줄 요약(B29)을 같이 적는다.

### `{{auto_analysis}}` 생성 규칙

**이 칸이 이 문서의 값이다.** 네 줄을 항상 이 순서로 낸다. 조건이 안 맞으면 그 줄의 else 문장을
낸다. 줄을 빼지 않는다 — 빠지면 읽는 사람이 "안 나온 건지 없는 건지" 알 수 없다.

| 줄 | 판정 | 참 | 거짓 |
|---|---|---|---|
| ① 집중도 | 슬롯 3개 이상 · 상위 2슬롯 점유율 `top_share ≥ 60%` | `발생이 {slots}에 {share}% 집중(판정 기준 60%) → 부품 Lot보다 공정·설비 원인을 먼저 의심한다.「근거」` | `슬롯 분포가 고르다(최대 {max_share}%) → 부품 Lot·입고 원인을 먼저 의심한다.「근거」` · **슬롯이 1~2개면 판정하지 않고** `발생 슬롯 {slot_code} {n}건 (보드당 {slot_count}개).「근거」` |
| ② 레시피 상관 | `first_exceeded_at`과 `recipe_versions.applied_at` 차 `≤ 3일` | `최초 초과({d1})가 {recipe} 적용({d2})과 3일 이내 → 변경 내용 '{change}'이 1순위 확인 대상.「판단자료」B` · `{change}`는 `recipe_versions.change_note`. **행이 없으면 `변경 내용 '…'` 절만 빼고 나머지는 그대로 낸다** | `최근 {window_days}일 내 레시피 변경 없음 → 부품 Lot·설비 마모를 먼저 본다.「판단자료」A` |
| ③ 재발 | 같은 `(part_id, defect_type)`의 `CLOSED` 대책서가 365일 내 존재 | `동일 부품·유형 CLOSED 대책서 {n}건({date} · {cause}) → 재발. 당시 대책이 왜 듣지 않았는지 먼저 확인한다.「판단자료」C` · `{cause}`는 그 문서의 `root_cause_label`. **비어 있으면 `· {cause}` 부분만 뺀다** | `동일 부품·유형 과거 대책서 없음 → 신규 발생.` |
| ④ 대체품 | 그룹 연결 있고 대체 후보 `n ≥ 1` | `{group} 대체 후보 {n}종 · {defect_type} 관련 소견 {m}종.「대체품」` (`m = 0`이면 `소견 미작성`) | 후보가 없으면 `{group} 대체 후보 없음 — {사유}.「대체품」` (`단일 소스 · 대체 불가` / `조사 필요` 를 그대로 싣는다) · 연결이 없으면 `연결된 데이터시트 없음 — 「대체품」 비어 있음.` |

**슬롯이 1~2개면 ① 을 판정하지 않는다.** 상위 2슬롯 점유율이 정의상 항상 100%라, 데이터와
무관하게 "집중 → 공정·설비 원인" 이 나온다. `GPU` 는 보드당 1개, `IND` 는 2개다.
이때는 슬롯별 건수를 그대로 싣는다 — 슬롯이 그것뿐이면 그게 이미 분포 전체다.

### 반올림은 half-up 으로 고정한다

`{top_share:.1f}` 같은 소수 한 자리는 **경계에서 갈린다.** 상위 2슬롯 13건 / 전체 16건은
정확히 `81.25%` 인데, 파이썬 기본 포맷은 half-even 이라 `81.2` 로 내려가고 엑셀과 사람은
`81.3` 을 기대한다. 문서에 찍힌 숫자가 재계산과 어긋나면 회신본 검증에서 걸린다.

```python
from decimal import Decimal, ROUND_HALF_UP
Decimal(str(x)).quantize(Decimal("0.1"), rounding=ROUND_HALF_UP)
```

**판정 임계(60%)도 이 반올림 뒤의 값으로 비교한다.** 그래야 문서에 적힌 수치와 판정이
같은 값을 본다.

임계값 `60%` / `3일` / `365일`은 상수다. `thresholds` 테이블에 넣지 않는다 — 판정 기준이
아니라 문장 생성 기준이고, 바뀌면 문서 문장이 통째로 바뀌므로 코드에서 보이는 편이 낫다.

## 왜 파일을 쪼개지 않았나

보고 내용과 판단 지침은 역할이 다르지만, **파일이 아니라 시트로 나눈다.**

- 자동발송의 목적이 담당자 손을 더는 것인데, 첨부가 2~3개면 회신 대상이 흐려진다.
  회신은 언제나 이 파일 1개다.
- 원인 추적은 왕복 작업이다. 현황 → 근거 → 추세 → 다시 현황. 파일이 갈리면 창 전환이고
  시트 탭이면 클릭 한 번이다.
- 회신본이 나중에 감사·고객 대응 근거가 된다. 판단 근거가 딴 파일에 있으면 짝이 어긋난다.
- 결재는 이미 분리돼 있다. 「대책서」 시트에만 `print_area`가 걸려 있어 A4 1장만 인쇄된다.
  별지는 인쇄 대상이 아니다.

쪼개야 하는 것은 파일이 아니라 **자료의 수명**이고, 그건 위의 [발행 시점 고정] /
[조회 시점 참조] 표기로 처리했다.

같은 이유로 **⑤⑥ 은 「검증」 시트로 뺐다.** ①~④ 는 발행 후 1~2주 안에 쓰지만 ⑤ 는 대책을
적용하고 다시 생산이 돌아야 채울 수 있어 2~4주 뒤고, ⑥ 은 그 다음이다. 작성 시점이 다른
칸을 한 장에 두면 담당자는 늘 절반이 빈 문서를 보고, 결재선은 미완성 문서를 받는다.
회신 칸은 좌표가 아니라 정의된 이름으로 읽으므로 **파서 계약은 그대로다.**
