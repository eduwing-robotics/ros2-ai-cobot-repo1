# 불량대책서 표준양식 — 필드 매핑

`불량대책서_표준양식.xlsx`의 `{{token}}`을 `scan_quality.py`가 치환한다.
샘플: `불량대책서_표준양식_샘플.xlsx`

시트는 4장이지만 **결재 대상은 「대책서」 1장**이다. 나머지 3장은 담당자가 원인을
좁히는 데 쓰는 별지이며, 자동 조회 결과라 사람이 손대지 않는다.

| 시트 | 용도 | 자료 성격 | 원본 |
|---|---|---|---|
| 대책서 | 보고·결재 (A4 1장) | 발행 시점 고정 | `defect_report.alerts` + 담당자 회신 |
| 근거 | 어느 유닛·슬롯에서 났는지 | 발행 시점 고정 | `defect_report.alert_evidence` |
| 판단자료 A~C | 언제부터·무엇이 바뀌어서 났는지 | 발행 시점 고정 | `production` 집계 + 과거 `alerts` |
| 판단자료 D | 무엇을 확인해야 하는지 | 조회 시점 참조 | `part_catalog.quality_checklists` |
| 대체품 | 부품을 바꿔야 할 때의 선택지 | 조회 시점 참조 | `part_catalog.part_candidates` + `part_supply` + `sources` |

**고정과 참조를 섞지 않는다.** 고정 자료는 발행 시점 스냅샷이라 나중에 집계가 바뀌어도
덮어쓰지 않는다(`Information.md` 2.2). 참조 자료는 데이터시트를 다시 적재하면 값이
바뀌므로, 시트 상단에 조회 시각과 데이터시트 기준일을 반드시 함께 싣는다. 특히 단가·재고·
리드타임은 발행 며칠 뒤면 틀린 값이 되므로 "발주 전 재확인" 문구를 지우지 않는다.

## 선행 조건 — `part_id` ↔ `group_id` 연결

`GET /parts/{part_id}`(조회 9 "부품 데이터시트와 대체 후보")와 「대체품」·「판단자료 D」
시트는 `alerts.part_id`에서 `part_catalog`로 넘어갈 수 있어야 성립한다.
**현재 스키마에는 그 경로가 없다.**

- `production.parts.part_id` = `HBM` `PM` `GPU` `CAP` `IND` `VRM` (004_mock_seed.sql)
- `part_catalog.part_groups.group_id` = `C-001` 형태 (데이터시트 Components 시트)
- 두 테이블 사이에 FK도 공통 키도 없다

연결 테이블을 `part_catalog`에 두는 것을 권한다. `production`에 컬럼을 추가하면 셀의
ROS2 계층이 소유자가 되어 경계가 어긋나지만, `part_catalog`는 데이터시트 로더가
쓰기를 소유하므로 소유권이 바뀌지 않는다.

```sql
CREATE TABLE IF NOT EXISTS part_catalog.part_group_links (
    part_id  text PRIMARY KEY,
    group_id text NOT NULL REFERENCES part_catalog.part_groups(group_id),
    load_id  bigint NOT NULL REFERENCES part_catalog.datasheet_loads(load_id)
);
```

데이터시트 Components 시트에 `part_id` 열을 하나 추가해 로더가 함께 적재하면 된다.
연결이 없는 부품은 「대체품」 시트를 `해당 데이터시트 없음`으로 비우고 발행한다.
문서 발행이 이 연결에 막혀서는 안 된다.

## 시트 `대체품`

`part_catalog.part_candidates`에서 해당 `group_id`의 전 행. 주품목 1행이 맨 위(노란
배경)에 오고 대체 후보가 뒤따른다. 후보 수 제한 없음 — 데이터시트에 있는 만큼 싣는다.

4행에 조회 시각·데이터시트 기준일·`group_id`·후보 수를 싣는다. 6행이 머리글, 7행부터 데이터다.

| 열 | 원본 |
|---|---|
| A | `part_candidates.candidate_role` |
| B | `part_candidates.alternate_code` |
| C~E | `manufacturer` / `manufacturer_part_number` / `key_spec` |
| F~I | `lifecycle_status` / `compatibility_status` / `revalidation_items` / `note` |
| J~Q | `part_supply.*` (공급사 · SPN · 단가 · 통화 · MOQ · 재고 · 리드타임 · 확인일) |
| R~S | `sources.source_id` / `sources.url` + `verified_content` |

`part_supply`에 행이 여러 개면 `price_checked_at`이 가장 최근인 1행을 싣고, 나머지는
`GET /parts/{part_id}`로 넘긴다. 문서에 공급사 표를 겹쳐 싣지 않는다.

## 왜 파일을 쪼개지 않았나

보고 내용과 판단 지침은 역할이 다르지만, **파일이 아니라 시트로 나눈다.**

- 자동발송의 목적이 담당자 손을 더는 것인데, 첨부가 2~3개면 회신 대상이 흐려진다.
  회신은 언제나 이 파일 1개다.
- 원인 추적은 왕복 작업이다. 현황 → 근거 → 추세 → 다시 현황. 파일이 갈리면 창 전환이고
  시트 탭이면 클릭 한 번이다.
- 회신본이 나중에 감사·고객 대응 근거가 된다. 판단 근거가 딴 파일에 있으면 짝이 어긋난다.
- 결재는 이미 분리돼 있다. 「대책서」 시트에만 `print_area`가 걸려 있어 A4 1장만 인쇄된다.
  별지는 인쇄 대상이 아니다.

쪼개야 하는 것은 파일이 아니라 **자료의 수명**이고, 그건 위의 [발행 시점 고정] /
[조회 시점 참조] 표기로 처리했다.
