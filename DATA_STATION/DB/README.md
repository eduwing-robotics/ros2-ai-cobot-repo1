# 생산 데이터 설계

`production_schema.sql`은 생산 데이터 계약의 기준 원본입니다. 이 문서는 테이블과 컬럼을 반복하지 않고, 스키마가 보장해야 할 업무 의미와 소유 경계만 설명합니다.

## 소유 범위

생산 데이터는 다음 사실을 보존합니다.

- 어떤 제품과 부품 구성이 생산 대상으로 정의됐는가
- 사용자가 어떤 PASS 수량을 요청했는가
- 각 생산 시도가 조립과 검사를 어떻게 끝냈는가
- 어떤 슬롯에서 어떤 불량이 확인됐는가
- 실제 생산에 따라 재고가 왜 변했는가

데이터베이스 서버 운영, HTTP 처리, 레시피 실행과 설비 제어는 이 폴더의 책임이 아닙니다.

## 핵심 관계

```text
Product ──< Product Slot >── Part
Product ──< Job ──< Unit ──< Unit Defect >── Product Slot
Part ──< Inventory Movement >── Unit
```

Job은 생산 요청이고 Unit은 실제 생산 시도입니다. 이 둘을 분리해야 검사 FAIL 뒤 재시도하더라도 요청 수량과 생산 이력을 모두 보존할 수 있습니다.

## 상태 불변 조건

- Job의 요청 수량은 PASS 목표 수량입니다.
- 동시에 `RUNNING`인 Job은 하나입니다.
- 한 Job에서 동시에 `RUNNING`인 Unit도 하나입니다.
- 검사 FAIL Unit은 완료된 시도로 남고 목표 PASS 수에는 포함하지 않습니다.
- 실행 실패 Unit은 `FAILED`로 남습니다.
- 제품 정의는 생산에 사용된 뒤 과거 의미가 바뀌지 않아야 합니다.
- 재고 현재값과 변동 원장은 같은 생산 사실을 가리켜야 합니다.
- 불량은 Unit과 제품 슬롯을 함께 식별해야 합니다.

가능한 불변 조건은 애플리케이션 관례가 아니라 DB 제약조건으로 보장합니다.

## 쓰기 권한

MainServer는 새 Job 등록만 담당합니다. Sequencer는 Job·Unit 실행 상태, 검사와 재고 기록을 담당합니다. 조회 전용 사용자는 생산 사실을 변경할 수 없습니다.

권한은 역할별 최소 범위로 나누며, 런타임 구현이 바뀌어도 이 구분을 유지합니다.

## 저장하지 않는 데이터

다음 데이터는 production 스키마의 소유가 아닙니다.

- 레시피 본문과 조립 단계
- 설비 좌표와 캘리브레이션
- 실시간 관절·TCP·카메라 스트림
- 중간 단계 checkpoint
- 부품 공급 후보와 가격 원본
- 불량대책서 파일과 담당자 회신

DB에는 실행에 사용한 레시피 버전과 확정된 결과만 기록합니다.

## 변경과 검증

스키마 변경은 기존 생산 사실을 보존하는 migration으로 적용합니다. 변경 후에는 제약조건, 역할 권한, Job·Unit 상태 전이와 재고 원장을 검증합니다.

- 기준 DDL: `production_schema.sql`
- 역할 권한: `005_roles.sql`
- 검증 SQL: `003_smoke_test.sql`
- 조회 예시: `002_query_samples.sql`
- 도식과 생성 결과: `diagrams/`
